# AI Compass — минимальная структура для Codex (MVP v0.1)

## Цель

Собрать **односессионный адаптивный онбординг**, который не привязывается к первой названной проблеме пользователя, собирает независимые сигналы в разных сферах жизни, поддерживает несколько гипотез, выбирает следующий вопрос по приблизительной информационной ценности (EIG) и завершает сессию 2–3 применимыми возможностями AI. Вопросы динамические; визуальные механики заранее подготовлены.

Это **план реализации для проверки гипотезы**, а не полная продуктовая архитектура. RRS и EIG — внутренние прототипные показатели AI Compass, а не функции OpenAI API; их формулы необходимо сделать явными, простыми и тестируемыми.

## Данные и цикл

```
Пользователь отвечает
  → POST /api/turn (сервер)
  → анализ ответа через OpenAI (строгий структурированный вывод)
  → обновление памяти текущей сессии
  → обновление гипотез + охвата разных сфер
  → вычисление RRS, приблизительного EIG кандидатов
  → решение: ещё вопрос / итог
  → выбор готовой механики + адаптация текста / выдача 2–3 сценариев
  → сохранение состояния в sessionStorage браузера
```

API-ключ хранится только на сервере. Браузерное состояние **считается недоверенным**, валидируется при каждом запросе и ограничивается по размеру. Не хранить приватные ответы в URL или журнале ошибок. Не передавать в OpenAI медицинские диагнозы как выводы системы.

## Минимальные функции

### OpenAI / извлечение смыслов

- `analyzeTurn(answer, sessionSummary, allowedMechanics)` — извлечь подтверждённые сигналы и сомнения; предложить **несколько** гипотез и 2–3 вопроса-кандидата, включая вопрос вне доминирующей темы. **Не** отдавать модели право самостоятельно завершать сессию.
- `validateAIOutput(raw)` — валидировать структуру ответа, допустимые механики, ограничения длины и отсутствие неподтверждённых диагнозов; при ошибке использовать безопасный резервный вопрос.

### Состояние и принятие решений

- `mergeSignals(session, signals)` — сохранить факты с источником, уверенностью, сферой; не превращать одну фразу в доказанную потребность.
- `updateHypotheses(session, hypotheses)` — поддерживать альтернативы и понижать уверенность при противоречиях.
- `calculateCoverage(session)` — оценивать, сколько **разных областей жизни** исследовано независимо.
- `calculateRRS(hypothesis, session)` — прототипная прозрачная оценка готовности конкретной рекомендации на базе доказательств и разнообразия сигналов.
- `estimateEIG(candidate, session)` — **эвристическая** оценка ожидаемой полезности вопроса; не выдавать её за математически откалиброванную информационную теорию.
- `selectNextAction(session, candidates)` — выбрать готовую механику и содержание либо перейти к результату; бороться с зацикливанием, дублированием и чрезмерной длиной сессии.
- `shouldFinish(session)` — проверять условия: достаточно проверенных сигналов, разнообразный охват, лимит ходов и возможность выдать применимые сценарии. Если лимит достигнут, выдать осторожный результат с пометкой об ограниченной уверенности.
- `buildRecommendations(session, opportunities)` — показать **2–3 открытия из разных сфер**, каждый с реальным первым шагом и ссылкой только на локально проверенный инструмент/сценарий.

## Контракт API

Вход `POST /api/turn`: `{ session: SessionState, answer: UserAnswer }`.

Выход: `{ session: SessionState, action: { type: 'question' | 'results', ... } }`.

Модель возвращает строго структурированное промежуточное содержимое; сервер принимает окончательное решение и нормализует итоговый ответ. Для Responses API использовать Structured Outputs с поддерживаемой JSON Schema и `store: false`; избегать несуществующих параметров и проверить SDK установленной версии по актуальным официальным инструкциям. Для отладки можно логировать только обезличенные времена/типы ошибок, не сами ответы пользователя.

## Критерии приёмки (MVP)

1. После ответа «ищу работу» система **не** выдаёт немедленно только карьерные рекомендации, а исследует минимум ещё одну независимую сферу.
2. Форма UI не создаётся моделью: AI выбирает из заранее заданного набора, меняя текст и варианты.
3. RRS и approximate EIG вычисляются кодом, а не необъяснимыми числовыми утверждениями модели.
4. При каждом следующем ответе меняются память, гипотезы и показатели; есть ограничение на повтор вопроса.
5. На выходе — 2–3 предложения из разных сфер, понятное «почему» и первый практический шаг.
6. Нет аккаунтов, постоянных профилей, автоматического обновления инструментов, Hugging Face/GitHub-поиска, сложной аналитики и внешних интеграций.
7. API-ключ нельзя увидеть в клиентском коде; при недоступности OpenAI приложение показывает понятную ошибку или безопасный резервный шаг.
8. Тестируется сценарий с противоречивыми ответами, пропуском, неинформативным ответом и попыткой повторно предложить вопрос из той же темы.

## Короткое задание Codex

> Работай в существующем репозитории AI Compass. Сначала изучи текущую структуру и переиспользуй существующие компоненты. Реализуй минимальный односессионный adaptive onboarding engine по этому документу: один server-only вызов OpenAI Responses API на пользовательский ход; строго структурированные сигналы/гипотезы/кандидаты вопросов; память в текущей сессии; вычисляемые в TypeScript RRS, approximate EIG и coverage; защита от зацикливания на первой проблеме; выбор только из готовых UI-механик; итог из 2–3 практических AI-возможностей с первым действием. Не реализуй регистрацию, постоянную базу пользователей, живой поиск, crawler или расширяемую агентную инфраструктуру. Покажи изменения по файлам, запуск проекта, простые автотесты и известные ограничения. Не придумывай калиброванные формулы RRS/EIG — используй прозрачные тестовые эвристики и явно пометь их как гипотезы.
